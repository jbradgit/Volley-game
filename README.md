# SCORDAGOL

[![CI](https://github.com/jbradgit/Volley-game/actions/workflows/ci.yml/badge.svg)](https://github.com/jbradgit/Volley-game/actions/workflows/ci.yml)

**SCORDAGOL** is a browser football **volley** game: balls are crossed in, you time
your volley, and you try to beat the keeper. It started as a love letter to the
pick-up-and-play Flash sports games of the 2000s and has grown into its own game with
a full career universe — domestic league and cup, European competitions, and
international tournaments.

Play it in a browser. There's no install, no account, and no tracking.

---

## Run it locally

The whole game is one HTML file, but it **must be served over HTTP** — opening it
directly as a `file://` URL taints the canvas and breaks the keeper's save detection.

**Windows:** double-click **`play.bat`**. It serves the game on
`http://localhost:5578/index.html` and opens your browser. Keep the window open while
you play; close it (or run `stop.bat`) to stop the server.

**Any OS:** you just need Python 3.

```sh
python3 serve.py                 # no-cache dev server on http://localhost:5578
#   ...or any static server, e.g.:
python3 -m http.server 5578      # then open http://localhost:5578/index.html
```

`serve.py` disables caching (so a refresh always loads your latest edits) and binds to
localhost only.

## How it's built

- **The entire game is [`index.html`](index.html)** — ~3,000 lines of vanilla
  JavaScript and Canvas 2D. **No framework, no build step, no dependencies.** Edit the
  file, refresh the browser, done.
- **Art** lives in [`assets/`](assets) and is generated by Python scripts in
  [`artgen/`](artgen) (the kit/recolour system, the 3D pre-rendered sprite pipeline,
  the stadium and UI art).
- **Specs** that the engine and the art generators both depend on live in
  [`docs/`](docs).

### The one rule: physics & scoring are sacred

The shot physics and scoring (`logicStep()`, `savedCheck()`, and the constants block in
`index.html`) are **transcribed from the original game and must not change** without
re-verifying that outcomes are identical. Everything else — rendering, UI, game modes,
the career universe, all the art — is fair game and evolves freely.

To protect that line, there's a headless regression test.

## Test

```sh
node ci/smoke.js     # exit 0 + prints "SMOKE PASS"
```

`ci/smoke.js` loads the game in Node with DOM stubs and drives the real engine through
its `__dbg` harness: timing sweeps, a connecting shot, a scored goal, full render
frames, and two complete winning career seasons — asserting **golden outcomes**
(shot resolution, goal score, season event counts, trophies, kit build). If a change
shifts the transcribed physics, this test goes red.

It runs automatically on every push and pull request via
[GitHub Actions](.github/workflows/ci.yml). **Always run it before pushing.**

## Deploy

`main` is the live branch — **GitHub Pages publishes it automatically** (~1–2 minutes
after a push). So landing a change on `main` *is* the deploy. The flow:

```sh
node ci/smoke.js                          # must pass first
git checkout main && git merge --ff-only <feature-branch>
git push origin main                      # Pages republishes
```

Test changes on `localhost` first; `main` is the public stage. Full details — including
the conventions and gotchas — are in [`HANDOVER.md`](HANDOVER.md).
